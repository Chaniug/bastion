# 本地数据库统一同步架构重构计划

> 状态：待用户确认 | 分支：dev | 创建：2026-08-19
> 关联：基于 KeePass 兼容性审计后的架构梳理

## 一、现状：三条互相纠缠的同步通路

经代码实证，当前 app 存在**三条独立同步通路**，逻辑重叠且用户认知负担大：

### 通路 A：KeePass kdbx 文件同步（`KeePassFileSource` 接口）
- 实现：`OneDriveKeePassFileSource.kt` / `WebDavKeePassFileSource.kt` / `LocalKeePassFileSource`
- 行为：把整个 kdbx 文件作为一个原子单元读写（read 字节 → 解析 → 本地视图 → 编辑 → 重新打包写回）
- 入口：`LocalKeePassOneDriveBrowser.kt`（OneDrive 浏览选 kdbx 文件）、`LocalKeePassViewModel.kt`
- 优点：与官方 KeePass 互操作、保留附件/历史/群组结构、单一文件易备份
- 局限：当前只支持"单个 kdbx 文件"挂载，多个库要切换

### 通路 B：Bitwarden vault 双向同步（`BitwardenSyncService`）
- 行为：把 Bitwarden 服务器 cipher 落到本地 `password_entries`，本地编辑可写回（`bitwarden_local_modified`）
- 优点：跨设备、多端
- 局限：与 kdbx 是两套独立数据源，本地表是"混合视图"

### 通路 C：选择性 zip 备份（`OneDriveBackupScreen` / `WebDavBackupScreen` + `SelectiveBackupCard`）
- 行为：用户勾选"条目类型"（密码/验证码/卡包/Passkey 等），`BackupContentPolicy` 筛选本地条目，打成 **zip** 上传 OneDrive/WebDAV
- 问题：**这是用户困惑的根源**——它不是同步 kdbx，是"本地条目按类型挑选后打包"，与通路 A 的 kdbx 文件同步是两码事，但 UI 上都叫"备份"
- `BackupContentPolicy.sanitizePasswordForBastionBackup` 还会清空 keepass/bitwarden 归属字段，让导出条目"脱离"原存储源——数据关系进一步混乱

### 本地表的"统一视图"困境
`PasswordEntry` 一张表承载三种来源（本地原生 / keepass 镜像 / bitwarden 镜像），靠 `keepassDatabaseId` / `bitwardenVaultId` 字段区分。结果是：
- 同一条目可能既属 keepass 又属 bitwarden（字段都非空）
- `isLikelyDetachedKeePassPassword` 这种"脱离判定"逻辑复杂且易错
- 备份时不知道该按"原存储源"还是"本地条目"处理

## 二、用户诉求（原文归纳）

1. **OneDrive 同步应直接读写 kdbx**，不要"备份内容选择"——从 OneDrive 读 kdbx、改了/加了条目、直接写回 kdbx
2. 若一定要存本地数据库，**导出时应提示选格式**（Bitwarden JSON / KeePass kdbx）——目前导出已有这些功能
3. 本地数据库应**推荐与 Bitwarden 或 OneDrive 上的 kdbx 连接起来**

## 三、Bitwarden 定位决策（2026-08-19 用户确认方向）

**结论：Bitwarden 保持"独立云端源"，与 kdbx 新架构并行，不降级为 kdbx 文件。**

事实依据（代码实证）：
- Bitwarden 是 REST API 云服务，非文件。`bitwarden_vaults` 存账户，cipher 双向同步到 `password_entries`（`bitwardenVaultId`/`bitwardenCipherId`/`bitwarden_local_modified`）
- Bitwarden 官方互操作格式是 JSON（含加密 JSON），不是 kdbx
- UI 已有来源区分（云图标）与存储目标选择（`MultiStorageTargetSelectorCard`）

具体处理：
1. **Bitwarden 用户**：数据在官方服务器天然云备份 → **OneDrive zip 备份对 Bitwarden 用户冗余**，退役通路 C（选择性 zip 备份）
2. **kdbx 用户**：OneDrive/WebDAV/本地文件挂载 kdbx 为主路径（通路 A 已有机制）
3. **导出统一**：按当前来源提示格式（kdbx / Bitwarden JSON / 加密 JSON / CSV）
4. **可选迁移出口**：Bitwarden 条目"导出为 kdbx"（`BitwardenJsonExport` 补 kdbx 映射），仅用于想离开 Bitwarden 的用户，非主路径

## 四、目标架构：kdbx 为本地数据库的"存储后端"

核心思路：**本地数据库不再是独立的 Room 表视图，而是"挂载在某个存储源上的 kdbx"**。

```
┌─────────────────────────────────────────┐
│  本地数据库（LocalKeePassDatabase）      │
│  ├─ 存储源：OneDrive kdbx / WebDAV kdbx │
│  │         / 本地文件 / Bitwarden vault  │
│  └─ 内存：kotpass KeePassDatabase 对象   │
│      （编辑即改内存，保存即写回源）        │
└─────────────────────────────────────────┘
        ↑                          ↑
   编辑/添加条目              保存触发写回
        ↓                          ↓
┌──────────────┐          ┌──────────────────┐
│ UI 展示/搜索  │          │ 存储源写入        │
│ （内存映射）  │          │ (kdbx 文件/vault) │
└──────────────┘          └──────────────────┘
```

### 关键变化
1. **本地数据库 = 挂载的 kdbx**：不再有"本地 Room 表 + kdbx 镜像"双份。打开本地库就是打开一个 kdbx（来自 OneDrive/WebDAV/本地文件）
2. **编辑直写 kdbx**：条目编辑直接改内存中的 `KeePassDatabase`，保存时整体写回存储源（通路 A 已有的机制）
3. **Bitwarden 作为独立存储源**：Bitwarden vault 仍双向同步，但不再与 kdbx 混在同一张表——要么单独的"Bitwarden vault"视图，要么导出为 kdbx 后挂载
4. **移除通路 C（选择性 zip 备份）**：备份 = 同步 kdbx 文件，不再有"按类型挑选打 zip"。原有 `SelectiveBackupCard` / `BackupContentPolicy` 退役
5. **导出统一入口**：从当前数据库（kdbx）导出为：kdbx（默认）/ Bitwarden JSON / Bitwarden 加密 JSON / CSV——已有功能，保留

### 兼容性
- 已有本地 Room 数据库的用户：首次升级时，把本地条目**一次性导出为 kdbx**（默认存到本地文件或 OneDrive），完成"本地表 → kdbx 文件"迁移；之后本地表只读，最终废弃
- Bitwarden 用户：Bitwarden vault 仍可用，但定位为"独立云端源"，不与 kdbx 混合

## 八、Bastion 工具多格式存储扩展（2026-08-22 实施，dev 分支）

> 状态：Phase 0 + Phase 1（后端 + UI）已落地，待 CI 全绿后合并 dev→main | 分支：dev
> 背景：原"KeePass 工具"仅绑定 kdbx。用户要求扩展为更通用的"Bastion 工具"，支持多格式、多来源，并具备上传/同步到 OneDrive 与 WebDAV 的能力。

### 8.1 支持的格式与来源

| 格式 | 扩展名 | 来源 | 加密 | 备注 |
|------|--------|------|------|------|
| KDBX | `.kdbx` | 本地 / OneDrive / WebDAV | 密码 + 可选密钥文件 | 既有 kotpass 链路，未改 |
| JSON | `.json` | 本地 / OneDrive / WebDAV | 可选（Bitwarden 加密格式，无密码即明文） | 复用 `BitwardenJsonExport/Import`，与导入导出互通；定位为**独立可同步云端库** |

**可新建格式收敛为 KDBX + JSON 两种**（2026-08-22 用户决策，避免与「导入数据」功能画蛇添足）：
- **CSV 从 Bastion 工具的创建入口移除**——CSV 进入 Bastion 已由现有「设置 → 导入数据」功能（支持 6 种 CSV 来源）全面覆盖；作为常驻/可同步库易丢字段（无卡片/自定义字段/文件夹结构）、价值低。
- 底层保留为**读旧文件兼容**：`BastionDatabaseFormat.CSV` 枚举值、`BastionDatabaseFormatCodec` 解析、`Converters`、`detectFormatFromPath`（对 `.csv` 仍返回 CSV）均保留——因枚举 exhaustive `when` 约束，删枚举值会引发大范围改动与 Room 迁移风险，故仅关闭 UI 创建入口。
- **不做**：Google Drive（用户明确不需要）。

### 8.3 字节流与格式解耦（核心设计）

JSON/CSV **完全复用** kdbx 既有的"来源 / 工作副本 / 远端同步 / 上传 Worker"抽象，仅在
「文件字节 ↔ Room 条目」这一层按 `BastionDatabaseFormat` 分派：

- **KDBX**：`KeePassKdbxService` 既有 kotpass 链路处理（本特性不改）
- **JSON/CSV**：由 `utils/BastionDatabaseFormatCodec.kt`（独立 `object`）负责解析与序列化
  - `createInitialContent(format, name, password, securityManager)`：新建空库字节
  - `importContent(format, bytes, password, keepassDatabaseId, context)`：解析并镜像进 Room（`passwordEntryDao` / `secureItemDao`），全部打 `keepassDatabaseId` 归属
  - `exportContent(format, keepassDatabaseId, password, context, securityManager)`：把 Room 最新条目导出回文件字节
  - CSV 用自研轻量解析器（`parseCsvContent` / `parseCsvLine` / `csvField`），无需第三方库

> 设计取舍：`LocalKeePassViewModel` 不持有数据仓储，构造点在 6 处（MainActivity、各 Add/Edit 屏、Autofill 等），
> 故"解析并镜像进 Room"抽成独立 `object`，直接用 `PasswordDatabase.getDatabase(context)` 的 DAO，避免改动 6 处构造与注入。

### 8.4 同步/上传分派（Phase 1，提交 `b0cb6b9` 及本次修复）

- `KeePassKdbxService.syncRemoteDatabase`：`databaseFormat != KDBX` 时转交 `syncBastionDatabaseFile(databaseId)`
- `syncBastionDatabaseFile`：每次同步先把 Room 重新 `exportContent` 到工作副本（确保本地编辑被纳入比对）→ 计算 workingHash → 读远端 `fileSource.stat()/read()` → 比较 remoteHash/workingHash/baseHash 与 etag/versionToken → 分四种情况（拉取 / 上传 / 冲突远端优先 / 最新）
- 纯本地库（非远端）：只重新 `exportContent` 写回工作副本
- 远端接入（`attachOneDriveDatabaseBlocking` / `attachWebDavDatabaseBlocking`）：根据 `detectFormatFromPath(remotePath)` 自动检测扩展名；JSON/CSV 走 `BastionDatabaseFormatCodec.importContent`，跳过 kdbx 诊断
- 冲突策略 v1：**远端优先**（拉取远端、本地改动不自动合并）
- `createWebDavDatabase` / `createOneDriveDatabase` / `createDatabase` 均新增 `format: BastionDatabaseFormat` 参数（默认 KDBX），按格式生成扩展名与初始字节
