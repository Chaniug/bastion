# 分支合并与发版流程

> 目标读者：接手本仓库的开发 / Agent。
> 本文固化「dev 开发 → 验证 → 合入 main → 发版」的操作步骤与已知坑，避免每次重新摸索。
> 更新时间：2026-08-30

---

## 一、分支策略

| 分支 | 职责 | CI |
|------|------|-----|
| `dev` | 开发、修复、测试。**默认分支**（`origin/HEAD`） | `Android CI debug`，push / PR 均触发 |
| `main` | 稳定分支，发版基线 | **不触发任何 CI**（见第四节） |

所有改动先进 `dev`，验证通过后再合入 `main`。

---

## 二、合入 main 的前置条件

1. **dev 的 CI 全绿**
   在 GitHub Actions 查看 `Android CI debug`，或用：
   ```bash
   gh api repos/Chaniug/bastion/commits/<dev-sha>/check-runs --jq '.check_runs[] | {name, conclusion}'
   ```
   关注注解里的 `Unit test stats: total=N failed=0 baseline=0 verdict=PASS` 与 `build_failed=false`。

2. **真机验证**（荣耀 / Android 17）
   从 `preview` release 下载 `app-arm64-v8a-debug.apk` 安装，验证本次改动涉及的功能点。

3. **确认无分叉**
   ```bash
   git fetch origin main
   git log --oneline dev..FETCH_HEAD | cat   # 为空 = main 未领先 dev，可安全合并
   ```

## 三、合并操作

### 3.1 本地合并（当前采用）

```bash
git fetch origin main
git checkout -b main FETCH_HEAD          # 本地无 main 分支时需先建
git merge --no-ff dev -m "Merge branch 'dev' into main: <本批改动摘要>"
git push origin main

# 关键：把 main 合回 dev，让两个分支重新对齐（见 4.3，否则 main 会一直领先 dev）
git checkout dev
git merge --ff-only origin/main
git push origin dev
```

采用 `--no-ff` 是为了保留合并节点，与仓库历史风格一致
（历史中均为 `Merge branch 'dev' into main: ...` 形式的 merge commit）。

**副作用**：merge commit 只存在于 main，会导致 `compare/main...dev` 显示
`behind_by=1`（dev 落后 main 1 个提交）。这是正常的——该 commit 内容为空，
`total_commits` 仍为 0。下次 dev 有新提交时会自然消解。

### 3.2 通过 PR 合并

```bash
gh pr create --base main --head dev --title "Merge dev into main: <摘要>" --body "<内容>"
gh pr merge <number> --merge            # 或 --squash / --rebase
```

**前提**：dev 必须领先 main（`ahead_by > 0`），否则 GitHub 拒绝创建空 PR。

### 3.3 合并后校验

```bash
# 内容应与 dev 完全一致
git diff dev main --stat | cat           # 应为空

# API 侧确认
gh api repos/Chaniug/bastion/compare/main...dev --jq '{ahead_by, behind_by, total_commits}'
# 期望：ahead_by=0, total_commits=0
```

## 四、已知坑

### 4.1 main 分支不触发任何 CI ⚠️

`.github/workflows/main.yml` 的触发配置：

```yaml
on:
  push:
    branches: [ dev ]        # 只监听 dev
  pull_request:
    branches: [ dev ]        # 只监听「目标分支为 dev」的 PR
```

后果：

- 直接 push 到 main → **不跑 CI**
- 开 dev → main 的 PR → **也不跑 CI**（目标是 main，不在监听列表）

因此 **main 上的代码没有自动化验证保护**，质量完全依赖 dev 阶段的 CI 与真机验证。
若需补上这个敞口，把 `main` 加入上述两个 `branches` 列表即可（属 workflow 配置变更，需确认后改）。

### 4.2 正式发版是手动触发

`Android Stable Release`（`.github/workflows/Android-Release.yml`）的触发条件是
`workflow_dispatch`，合并到 main **不会**自动发版。

```bash
gh workflow run Android-Release.yml --repo Chaniug/bastion --ref main
```

或在 GitHub → Actions → `Android Stable Release` → Run workflow。

### 4.3 「main had recent pushes N minutes ago」不是错误

这句话不是单纯的时间戳，需**两个条件同时成立**才显示：

1. 该分支最近被推送过
2. **该分支领先于默认分支（remote HEAD）**

> ⚠️ 本仓库的默认分支是 **`dev`**，不是 main。
> 用 `gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'` 可确认。

所以它出现的真正原因是：`--no-ff` 合并会在 main 上留下一个**只属于 main 的 merge commit**，
于是 main 领先 dev 1 个提交，提示就出现了。

**消除方法**：把 main 合回 dev（fast-forward），让 main 不再领先——这是标准做法，
顺带把两个分支重新对齐：

```bash
git checkout dev
git merge --ff-only origin/main
git push origin dev
```

完成后 `compare/main...dev` 应回到 `ahead_by=0 behind_by=0`，提示随之消失。

**两条取舍**：

| 方案 | 操作 | 代价 |
|------|------|------|
| A（当前采用）保留 merge commit | 每次合并后多一步「main 合回 dev」 | 多一条命令，换来清晰的合并节点、便于回滚 |
| B 改用 fast-forward 合并 | 无需额外操作，main 天然不领先 | main 历史变线性，失去合并节点 |

其他特性：提示约 2 小时后会自行淡出，且**只有推送者本人可见**
（其他人访问仓库看不到），所以通常只有自己在推送后撞见。

真正该警觉的信号是这三个（历次合并均无）：
- 提示伴随 **"This branch has conflicts"**
- PR 页面显示**文件差异**（而非 0 files changed）
- `compare` 的 `total_commits > 0` 且 diff 含预期外改动

### 4.4 推送通道

沙箱/本地环境 HTTPS(443) 可能被阻断，改用 **SSH(22)**：

```bash
git remote set-url origin git@github.com:Chaniug/bastion.git
```

详见 [GITHUB_NETWORK_NOTE.md](./GITHUB_NETWORK_NOTE.md)。
拉取慢时可走 CDN 镜像（`mirror` remote 指向 `ghfast.top`）。

### 4.5 artifact 保留期填多大都不生效（仓库上限 3 天）⚠️

**现象**：CI 日志里反复出现这条 warning：

```
Retention days cannot be greater than the maximum allowed retention set within the repository. Using 3 instead.
```

**原因**：仓库 `Settings → Actions → Artifact 保留上限` 是 **3 天**。workflow 里
`retention-days` 填 7 / 14 / 30 都会被 GitHub 静默降级成 3，配置值与实际生效值不符，
注释里写的「14 天足够回溯」会误导后续维护。

**现状**：2026-08-31 已把 6 处全部显式改成 `3`，分布在：

| 文件 | 产物 |
|------|------|
| `.github/workflows/main.yml` | debug APK / 单测报告 / compose 编译器报告 |
| `.github/workflows/Desktop-Build.yml` | 桌面安装包（单份约 169 MB） |
| `.github/workflows/regenerate-lint-baseline.yml` | lint 日志 / baseline 兜底 |

**怎么确认当前上限**（API 读不到，只能从 warning 反推）：

```bash
# job_id 取 gh run view <run_id> --json jobs --jq '.jobs[0].databaseId'
gh api repos/Chaniug/bastion/check-runs/<job_id>/annotations \
  --jq '.[] | select(.message | test("Retention days")) | .message'
```

注意 `gh api repos/{owner}/{repo}/actions/permissions` 的 `artifact_retention_days`
对公开仓库通常取不到值，别拿它当依据。

**需要更长留存时**：先去仓库 Settings 调高上限，再改 workflow；顺序反了写了也不生效。

## 五、预览包获取

CI 通过后在 `preview` release 发布 `app-arm64-v8a-debug.apk`：

```bash
gh api repos/Chaniug/bastion/releases/tags/preview --jq '.assets[] | {name, size, updated_at}'
```

沙箱内直连 `release-assets.githubusercontent.com` 常失败，可走镜像：

```bash
curl -sL -o app.apk "https://ghfast.top/https://github.com/Chaniug/bastion/releases/download/preview/app-arm64-v8a-debug.apk"
```

下载后建议与 API 返回的 `size` 比对字节数，确认拿到的正是最新构建。
